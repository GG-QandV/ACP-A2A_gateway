# Р-20. Стриминг реализован (Фаза 2) — дополнение к Р-18

("почему было не реализовано"), эта запись фиксирует "как было реализовано и что осталось вне

### Р-20. Стриминг реализован через `prompt_streaming()`, не через изменение `prompt()`

Р-18 фиксировал `Reply<T,U>` как готовый seam с `Streaming`-вариантом без реализации. Реализация
пошла НЕ через замену тела существующего `prompt()`, а через новый метод трейта с дефолтной
реализацией:

```rust
// core/src/agent.rs, trait AcpAgent
async fn prompt_streaming(&self, req: PromptRequest) -> anyhow::Result<Reply<PromptResponse, SessionUpdate>> {
    self.prompt(req).await  // дефолт = старое нестриминговое поведение
}
```

Рассматривался прямой вариант — переписать сам `prompt()`, чтобы он возвращал `Reply::Streaming`
всегда, когда есть чем стримить. Отвергнут: любой код, зовущий `.prompt()` (включая все существующие
тесты и `A2aAsAcp::prompt()` — направление 3, если для него в моменте не готова стрим-обработка на
вызывающей стороне), автоматически получил бы `Reply::Streaming` там, где ждал `Reply::Complete`, и
сломался бы без единой правки на своей стороне. Дефолтный метод устраняет этот риск полностью:
старое поведение доступно всем, кто не просил другого явно.

**Следствие:** `StdioAcpAgent` переопределяет `prompt_streaming()`, не `prompt()`. `convert.rs`
вызывает `prompt_streaming()` только там, где вызывающий код (транспортный слой) готов обработать
`Reply::Streaming`.

### Р-21. Стриминг Фазы 2.0 переносит только `AgentMessageChunk` — остальные `SessionUpdate` не парсятся

`collect_session_update()` в `core/src/stdio_agent.rs` фильтрует JSON на `sessionUpdate ==
"agent_message_chunk"` до создания типизированного `SessionUpdate`. Это ограничение существовало
и до стриминга (P2-1) — Фаза 2.0 его не убирает.

Явное сужение объёма, а не забытая работа: `AgentMessageChunk` — основной канал текстового ответа
и закрывает основную ценность стриминга (пользователь видит текст по мере генерации).
`ToolCall`/`ToolCallUpdate`/`Plan`/`UsageUpdate` требуют сверки с точной JSON-схемой ACP для каждого
варианта отдельно — риск непропорционален ценности для первой итерации.

Маппинг этих 4 вариантов в `core/src/convert.rs::session_update_to_a2a_event()` **написан и
оставлен в коде**, но недостижим при текущем фильтре `collect_session_update()` — это сознательно,
не мёртвый код для удаления, а готовность к следующей итерации, когда парсинг расширится.

**Облако/будущее:** расширение парсинга `tool_call`/`plan`/`usage_update` — отдельный тикет,
не блокирует релиз текущей реализации стриминга.

### Р-22. `tasks/resubscribe` не входит в объём Фазы 2.0

TECH_DEBT.md (пункт "стриминг в конвертерах не реализован") называет `tasks/resubscribe ↔
session/update` маппинг частью fix. Реализованная в Фазе 2.0 модель — `mpsc::UnboundedSender`,
живущий только на время одного активного вызова `prompt_streaming()` (запись в
`StreamSendersMap` удаляется сразу после завершения хода) — принципиально не подходит для
resubscribe: как только клиент отвалился, канал закрыт, восстановить нечего.

Настоящий `tasks/resubscribe` требует персистентного буфера событий с sequence-номерами (модель
"Вариант B" из архитектурного разбора: `broadcast::channel` или лог событий прямо в `TaskStore`,
по образцу `after_seq`/`Last-Event-ID` в `driver_http_sse.rs` соседнего проекта `agent-connector`).
Это другая структура хранения потока, не точечное расширение уже сделанного — попытка добавить
resubscribe "на скорую руку" поверх эфемерного `mpsc`-канала создала бы заглушку, которая выглядит
рабочей, но не восстанавливает реальный поток данных.

**Решение:** `tasks/resubscribe` выносится в отдельный будущий тикет ("Фаза 2.1 — resume для
стриминга"), TECH_DEBT.md обновляется, чтобы не выглядело забытым куском текущей работы.

**Облако:** буфер событий с seq-номерами в `TaskStore` пригодится не только для resubscribe, но и
для устранения проблемы "continue по contextId таймаутит" (TECH_DEBT, направление 4) — общий
механизм переподписки на существующую задачу решает оба сценария одним кодом. При планировании
Фазы 2.1 оценить их совместно, не по отдельности.
