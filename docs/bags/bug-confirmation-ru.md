## Важное предостережение по `resolve_env_placeholders` — проверь до применения патча

Функция, как мы её писали, содержит тихий фолбэк:

```rust
fn resolve_env_placeholders(value: &str) -> String {
    if let Some(var_name) = value.strip_prefix("{env:").and_then(|s| s.strip_suffix('}')) {
        std::env::var(var_name).unwrap_or_default()  // ← если переменной нет — пустая строка
    } else {
        value.to_string()
    }
}
```

Если `GATEWAY_TOKEN` не экспортирован в окружении процесса gatewayd на момент старта, `tokens` получит **пустую строку** вместо ошибки — и тогда `check_token("")` будет либо ложно пропускать пустой Bearer, либо (что вероятнее) просто никогда не совпадёт ни с одним реальным токеном, но без явного сообщения о том, что переменная не найдена. Это отдельный, более тихий баг рядом с тем, что ты нашёл — стоит сразу заменить `unwrap_or_default()` на явную ошибку при старте, если будешь чинить.

## Как это применить с учётом ограничения "только готовые бинарники"

Раз cargo/rust с хоста удалены осознанно, патч в `main.rs` нужно собрать **не на этом хосте** — на CI или другой машине с тулчейном, а на `/srv/gateway` доставить только новый бинарник `gatewayd`. Порядок безопасного отката:

1. Собрать пропатченный `gatewayd` в другом окружении.
2. На хосте: `systemctl stop gatewayd` (или как он у тебя запущен), заменить бинарник, вернуть `config.yaml` к `tokens: ["{env:GATEWAY_TOKEN}"]` вместо raw-значений, убедиться что `GATEWAY_TOKEN` реально в `Environment=`/`.env` юнита.
3. Запустить, проверить логи на неожиданные пустые токены (см. предостережение выше) — стоит временно добавить лог `tracing::warn!` при пустом резолве, чтобы не словить тихий отказ всех клиентов.
4. Только после проверки — вернуть `chmod 600` на конфиг без plaintext-токенов внутри.

## Уточнение по сети — не баг, но стоит подтвердить намеренность

`http_listen: 172.17.0.1:8348` — это IP `docker0` моста, то есть HTTP-транспорт (направление 4, A2A-клиент→ACP-агент, плюс A2A↔A2A passthrough) слушает только на docker-мосте, недоступен с `127.0.0.1` или внешнего интерфейса напрямую — Traefik должен быть контейнером в той же docker-сети, чтобы достучаться. TCP на `127.0.0.1:8347` — наоборot, доступен только локально, ACP-клиенты снаружи хоста до него не достанут вообще. Если это осознанная топология (Traefik — единственная внешняя точка входа, TCP-транспорт используется только локальными процессами на хосте) — это нормально и совпадает с моделью "токен = allow/deny на вход" из спеки. Если TCP-направление тоже должно быть доступно снаружи — тут отдельная правка `listen:` в конфиге, не связанная с багом токенов.
